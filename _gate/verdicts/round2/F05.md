# Verdict — F05 (weight is earned by trace: born neutral)

Reviewer: zero-context skeptic, round 2. No prior exposure to ECHELON or to any earlier verdict.
Read: README.md, _gate/SKEPTIC-BRIEF.md, appendix/AP3-glossary.md, this finding.

**VERDICT: PASS**

## 1. Claim restated in one sentence

Every stored lesson enters the store at the same score its author cannot set, and that score can
only rise from an event the engine itself witnessed — a fetch through its own door, or the success
of a card that loaded the lesson — so ranking records what happened after writing rather than how
emphatic the writer was.

I could state it. Step 1 passes.

## 2. The evidence line

Found, and it is a witnessed run, not an intent quote. The four-line selftest of 2026-09-10 on a
throwaway scope:

```
[PASS] COMPILE earned_before={'score': 100.0, 'use_count': 0}
[PASS] RECALL  verdict=warm score=1.0; surfaced=YES
[PASS] EARN    served=yes  score 100.0 -> 102.0  use_count 0 -> 1  MOVED=YES
```

Three of the claim's four parts are directly observed by that transcript: born at a flat value with
use_count 0, a peek that does not move it, a fetch that does. The numbers are numbers, dated, and
from a run rather than a docstring. Step 2 passes on the claim as stated.

Two things in the Evidence section are *not* witnessed, and the finding says so itself rather than
letting me catch it. The earn constants (+2.0 / -10.0 / floor 1.0) are read out of a source module,
which is an implementation quote, not a run — but they are corroborated by the observed 100.0 ->
102.0 delta, so the +2.0 at least is witnessed twice. The `recall_peek` / `remember_fetch` docstrings
*are* quotes of intent, and if the finding rested on them it would fail here; it does not, because
the selftest independently demonstrates the free/paid split those docstrings describe. That
ordering — run first, docstring second as colour — is what keeps step 2 clean.

The fourth part of the claim, `card_success`, has no evidence line at all. See step 4.

**Credit where it is due, because it changes the verdict.** The finding does not claim the property
it failed to prove. It states outright that the 2026-09-08 ruling against the fetch constant has not
been merged, that the selftest shows the condemned 2.0 still moving, and — the sentence that saves
it — "So the selftest proves that a fetch is witnessed and that no author sets the score. It does
not prove that fetch has been separated from outcome, because on 2026-09-10 it had not been." A
finding that fences its own claim to what the run witnessed is judged on that fenced claim. The
narrow claim is evidenced.

## 3. Mechanism rebuilt from the text alone

The finding hands over five lines; the test is whether I can rebuild them without reaching outside
the file. I can:

```
add_atom(body):        row(score=100.0, use_count=0)          # author passes no score argument
recall_peek(id):       return spine(id)                        # no write, no earn
remember_fetch(id):    row.score += 2.0; row.use_count += 1; return body(id)
card_success(cid):     for a in atoms_loaded_by(cid): credit(a)
fire_lower(id, why):   row.score -= 10.0; decay toward 100.0; never delete
```

Everything in those five lines is in the text: the born value, the peek's non-mutation, the +2.0 and
the use_count increment (all three from the selftest), the -10.0 and the anchor (from the earn-law
paragraph and the `fire_lower` paragraph). Step 3 passes for four of the five lines.

`card_success` is the exception and I flag it as a partial gap rather than a fail. `credit(a)` has
no constant, no formula, and no witnessed run — the text says only that credit "is split across
every atom the card loaded". I cannot reimplement that line; I can only stub it. This matters more
than a missing constant usually would, because the finding names `card_success` as "the real earn"
and the *only* upward path that is not a tenure event. So the mechanism's headline verb is the one I
cannot rebuild. It is not a step-3 FAIL, because the claim as fenced in step 2 is about born
neutrality and the witnessed fetch, and both of those rebuild cleanly. It would be a FAIL for a
finding that claimed earn-by-outcome works.

## 4. One way it could be wrong that the text does not address

The finding's own objections section is unusually thorough — it already raises the unmerged fetch
constant, credit-splitting across adjacent atoms, phrasing-to-match-the-query as self-assertion
moved into the body, near-duplicate shelf space, who composes the card, and the `fire_lower` anchor
conflating "misleading" with "untried". That last one is a genuinely sharp self-catch. So I have to
work to find something outside it.

**Not addressed: the born value is only neutral within one scale, and nothing pins the scale.** The
Retractions section closes the 100.0-vs-0.31 conflict by saying they are the same value on two
scales. Grant that. But born neutrality is a claim about *ordering*, and ordering is only preserved
across a rescaling if the rescaling is monotonic and applied to every atom identically. The finding
demonstrates neither. If any atom is ever written, scored, or read under a different normalisation
than its neighbours — different node spec, different engine version, an import from another scope —
then two atoms both "born neutral" are born at different points in the shared ordering, and the
author's vote re-enters not through the score field but through which scale their atom was created
under. The falsification test given ("plant an atom, do not use it, its rank must be
indistinguishable from every other unused atom") is run once, on one scope, on one engine version,
on one day. It would not detect this. NOTE, not a FAIL.

**Second, smaller.** `use_count` moved 0 -> 1 in the same call that moved the score. If any part of
ranking or promotion reads `use_count` rather than score, a fetch buys rank through a second channel
that the "no author sets the score" property does not cover. The glossary's *effective score (two
surfaces)* entry already warns that stored and recomputed scores can disagree and that promotion
candidates read the stored one; a third quantity moving on the same witnessed event is unexamined.

## 5. Terms used before definition

Handled well. The finding opens with an explicit pointer to AP3 for atom, bank, seat, receipt,
weight, warmth, take-up, remember, recall, and then defines *receipt* inline anyway at first use
("a logged act the engine performed, carrying ids and re-runnable"). *hand-path*, *anchor* and *born
neutral* are all defined at first use in the body and again in AP3. *card* is defined inline as "an
ordered sequence of atoms that composes a procedure" — I flag this, because it does not match AP3,
which defines a card as "a record of one attempt to do a piece of work, including which atoms it
drew on and whether it succeeded". Those are different objects: one is a plan, the other is an
outcome record. Since the whole upward-credit path runs through `card_success`, a reader who takes
the inline definition will misread what succeeds. Minor but load-bearing.

*scope*, *wrap*, *ingest* are used before definition in-file but all sit in AP3, which the release
ships, so the reader named in README.md has them. Not flagged.

## Failing step

None. Step 3 is partial on `card_success`, step 5 has one definitional collision.

Second sentence, if only one more is available — the inline gloss of *card* as "an ordered sequence
of atoms that composes a procedure" should be reconciled with AP3's definition, since credit flows
through it.
